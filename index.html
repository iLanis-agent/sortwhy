SortWhy

The same list, sorted four real ways. Spot where they disagree, and see why.

Paste a list. SortWhy sorts it the way JavaScript's default sort() does (UTF-16 code units), the way Python, SQLite and C-locale sort do (code points), and with the two ASCII case-insensitive rules (SQLite NOCASE folds to lower case, sort -f folds to upper, so _ lands on opposite sides of a). For every step it names the character that decided it.

Open the app

Traps it shows: [10, 9, 1].sort() giving 1, 10, 9; an emoji sorting before a fullwidth letter in JavaScript but after it in Python; Banana before apple; -10 before -2 as text.

How it was tested

60,000 random lists (6 seeds) of strings mixing ASCII, accents, CJK, fullwidth letters, and characters from the astral planes. Engine output compared with: Python 3.10 sorted(), SQLite 3.37.2 ORDER BY with BINARY and NOCASE collations, GNU sort in the C locale (plain and -s -f), and node's Array.sort(): 360,000 comparisons, 0 mismatches. NOCASE ties are compared by their folded keys because SQLite does not define tie order. 15,000 numeric lists checked against Python sorted(key=float) and node's default number sort: 0 mismatches. A first seed was used while building. The node check uses the same engine family as the page, so it confirms the UTF-16 rule rather than testing it independently. Entirely client-side.

Not covered: locale-aware rules (Intl.Collator, ICU, sort in en_US), natural or version sort, Unicode normalization.
